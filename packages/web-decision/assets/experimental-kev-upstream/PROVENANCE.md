# Experimental Kev upstream reconstruction assets

This directory documents the opt-in model ID `experimental-kev-0.6b-q4f16-upstream`. Package verification requires its separate experimental candidate chunk to be included in the package build. This route is not the released Kev 0.3 model.

The stable model ID `kev-0.6b-q4f16` has a separate loading path. It loads the stable TVM WebGPU WASM and small runtime metadata bundled in the package, fetches the pinned ONNX external-data file from revision `5a827091b3d58fe4fdfc02a5a5b2ce364047d678`, and reconstructs the nine stable shards against the stable manifest. The stable WASM SHA-256 is `ecc2bdce793221f4f370890d2ac4ddcb6082b85da05a645f3554903768b03cb0`; the stable manifest SHA-256 is `57c554e757a96093669c1555e9e2564780c7eaba5e102b4fcd9ad0c535878fe2`. This stable `modelId` route does not accept `assetsUrl`; `assetsUrl` applies only to the legacy `model` route. The stable ID route uses this stable WASM, not the experimental q2-k128 WASM.

The experimental route is opt-in and has no default model selection or published q2-k128 TVM asset-pack URL. It bundles its separate q2-k128 candidate TVM WebGPU WASM and candidate manifest. The source checkout also carries a 394-record source-to-shard map, SHA-256 `bbe4279b99d995770bd3ba681d17cec07e4f083aeaaddffb0a3ce26d07e81065`. The candidate WASM SHA-256 is `78026118d5c1f85941f75e0929d88d72edfc1a0418895d3f26bf6738a506882d`; released 0.3 instead pins `5e995762514782786cf0230f7f88bf3b0f1db3499f9c44cea9a691539adee4b0`. No equivalence is claimed.

Both no-`assetsUrl` reconstruction paths—the stable model-ID route and the opt-in experimental route—fetch the external data from the immutable Hugging Face revision above. They enforce the exact 335,357,952-byte limit and source SHA-256 `777335dbc052e2e02ec7591f6eefcfb29e2c28caf52075e492d226fc27e0824b`, then expose only mapped shard responses to the per-file verifier. The existing 128 MiB per-asset limit remains in force. Stable shards are checked against the stable manifest; experimental shards are checked against the candidate manifest. A shard is cached only after its corresponding manifest length and SHA-256 checks succeed. The raw source is not placed in CacheStorage.

The experimental route is not verified for broad parity or decision quality and is not a distribution candidate. Observed Windows Chrome testing measured about 1.8 GiB aggregate Chrome working set during its online reconstruction and load. Further review of licensing, browser support, cache quota, and package URL behavior is required before any distribution decision.
