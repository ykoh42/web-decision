# Kev 0.6B official-checkpoint self-conversion

Updated 2026-11-12 KST. This note records the reproducible source inputs, official assembly path, and compatibility target for converting Kev 0.6B from its publisher's checkpoint into the project's TVM format. It does not change the existing provenance decision.

## Current direct-TVM status

The current implementation loads the pinned official checkpoint, merges its adapter, exports a PyTorch graph, and imports it directly into TVM Relax. It does not use ONNX as an intermediate. The current-code direct Q4 CPU build passed for one 22-token fixture using PyTorch 2.8.0, Transformers 4.57.6, PEFT 0.21.0, and TVM 0.27.0.post1. It quantized 196 linear weights and one embedding, replacing 196 MatMuls and one Gather. The wrapper uses the product's int32 token/mask inputs and fp16 output ABI. Against the pinned ONNX Q4 output used strictly as a reference, max absolute logit delta was `0.03369` (limit `0.15`), probability delta was `0.000114` (limit `0.001`), and the selected option matched both the reference and official FP32 source. The report is [`direct-tvm-q4-cpu-r11.json`](../tools/kev-converter/reports/direct-tvm-q4-cpu-r11.json), SHA-256 `4e1b80f5006e58768ccd9c43132562dc3f07312d085ff27027b148c0281d5b41`.

This proves a static `[1, 22]` Relax Q4 graph and LLVM CPU inference for one fixture. It does not prove dynamic shapes, the official serving range, TVM WebGPU execution, exact browser package integration, offline cache behavior, or release rights. The official serving code sets state and branch limits to 8,192 tokens in [`kev/serve.py`](https://github.com/jaredpalmer/kev/blob/37cb2f6155afec1054de2cc78dfd7c7dd24a956d/kev/serve.py#L16-L18); both limits remain required verification targets.

The converter's lightweight wrapper tests also cover two question branches, restarted positions, question isolation, right-padded batches, option score positions, and `Linear` transposition with and without bias. They use a capturing test backbone; they do not establish full-model numerical parity on those cases. Literal special-token escaping, left/internal padding, multiple-question model outputs, and serving-limit inputs still need end-to-end verification.

## How the checkpoint becomes the decision model

The official [`kev/evaluate.py`](https://github.com/jaredpalmer/kev/blob/37cb2f6155afec1054de2cc78dfd7c7dd24a956d/kev/evaluate.py#L35-L66) loader is the reference assembly path:

1. Read `head.pt`; load the pinned base with `DecisionModel(..., revision=meta["base_revision"], dtype=torch.float32)`.
2. Apply `PeftModel.from_pretrained(base, run)` and call `merge_and_unload()` while the backbone is fp32. The code describes this merge as exact in fp32.
3. Load `meta["head"]` into the model's `PointerHead` and evaluate.

The [training code](https://github.com/jaredpalmer/kev/blob/37cb2f6155afec1054de2cc78dfd7c7dd24a956d/kev/train.py#L213-L220) writes `head.pt` as a dict containing the pointer-head state, base ID and revision, LoRA rank, head dimension, and run metadata. The [model definition](https://github.com/jaredpalmer/kev/blob/37cb2f6155afec1054de2cc78dfd7c7dd24a956d/kev/model.py#L104-L170) defines two `Linear(1024, 256)` projections, `q` and `k`; each option score is `k(h_<|box_end|>) · q(h_<|fim_suffix|>) / sqrt(256)`. The model card identifies this as the pointer readout.

The adapter targets Qwen's `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, and `down_proj` in every layer at rank 16 / alpha 32. The base config has 28 layers and hidden width 1024. The five delimiters (`<|fim_prefix|>`, `<|fim_middle|>`, `<|box_start|>`, `<|box_end|>`, `<|fim_suffix|>`) reuse existing Qwen token IDs; the checkpoint training config sets `special_embeddings=0`, so it has no new embedding rows. It also sets `option_isolation=0`: the model still applies its block-causal mask so question branches do not attend to each other, but it does not mask each candidate option from the others. Official `encode()` and `branch_mask_batch()` create the packed IDs, restarted branch positions, and block-causal mask in Python. They are the semantic reference for any graph wrapper.

## Historical ONNX route (not used for the replacement artifact)

The earlier project prototype imported an ONNX graph. The details below describe that historical artifact and are retained for provenance comparison only. They are not the input, quantizer, or implementation route for the replacement artifact. The direct wrapper now derives Kev's segment IDs, restarted positions, block-causal mask, and score locations from token IDs; the model entrypoint remains the official merged backbone and separate pointer head.

At the required [ONNX Community revision](https://huggingface.co/onnx-community/kev-0.6b-ONNX/tree/5a827091b3d58fe4fdfc02a5a5b2ce364047d678), the q4f16 asset is `onnx/model_q4f16.onnx` (3,338,522 B; SHA-256 `26e059ddd954efd9897772b098db10b9eeda9b873984dc1c73b32a9ce177c7c8`) plus `onnx/model_q4f16.onnx_data` (335,357,952 B; SHA-256 `777335dbc052e2e02ec7591f6eefcfb29e2c28caf52075e492d226fc27e0824b`). Its [pinned model card](https://huggingface.co/onnx-community/kev-0.6b-ONNX/blob/5a827091b3d58fe4fdfc02a5a5b2ce364047d678/README.md) describes the compatibility target: 4-bit MatMul weights at block size 32, a quantized embedding, an fp32 pointer head, and fp16 elsewhere. These are target artifact facts, not a source attestation for our separately converted weights. The [TVM converter](../scripts/tvm_q4_operators.py) handles only `com.microsoft::MatMulNBits` and `com.microsoft::GatherBlockQuantized` with 4-bit weights, 32-value blocks, Qwen projection dimensions, and the packed signed-nibble representation. [`specialize_q4_direct.py`](../scripts/specialize_q4_direct.py) requires exactly 197 such nodes (196 linear projections plus the embedding); it simplifies shapes with value-free placeholders, then restores the original quantized nodes and external packed weights. [`build_tvm_q4.py`](../scripts/build_tvm_q4.py) imports that graph, and the build lock pins `onnxruntime==1.31.1`, `onnx==1.23.2`, `onnxsim==0.8.1`, and `apache-tvm==0.27.0.post1`; the source build pins TVM commit `7b5acb32bd271342a24130f4ef439ff6c2e52c6c` in [`setup_preview.sh`](../scripts/setup_preview.sh). The pinned [Kev encoder](https://github.com/jaredpalmer/kev/blob/37cb2f6155afec1054de2cc78dfd7c7dd24a956d/kev/model.py#L8-L35) sets `MAX_STATE=384` and `MAX_BRANCH=1024` (total packed input), and the current TVM prototype also caps sequences at 1,024. The target card's 8,192-token context does not establish that the official serving encoder or this TVM package accepts 8,192-token records.

The old ONNX quantization recipe is historical evidence only. The replacement path must quantize the official checkpoint's merged parameters directly for TVM and record its own algorithm, parameters, source hashes, and output hashes. The existing ONNX graph and weights are not used as inputs.

### Historical prototype plan (superseded)

1. Download only the pinned Kev and Qwen snapshots above; verify every LFS hash and preserve the tokenizer/config/license files. Load them with the official code and locked dependency versions, with the checkpoint's `base_revision`; merge LoRA in fp32 and restore `head.pt` state.
2. Make a small PyTorch wrapper around the merged backbone and pointer head. Match `encode()` exactly for delimiter IDs, branch-reset position IDs, padding, the basic block-causal question mask, and `<|fim_suffix|>` / `<|box_end|>` readout indices. Use the checkpoint flags (`option_isolation=false`, `special_embeddings=false`), not current defaults. First compare wrapper logits to `kev/evaluate.py` on records with multiple questions, multiple choices, padding, and restarted positions.
3. Export a floating-point ONNX graph with a documented opset, stable input/output names, and dynamic sequence dimensions. Run ONNX checker and ONNX Runtime parity against the wrapper. Then QOperator-quantize only backbone MatMuls and embedding Gather at 4 bits, block size 32; leave `head.q` and `head.k` floating point. Check the emitted custom-node attributes and tensor types against the local TVM converters. ONNX Runtime's int4 documentation requires opset 21 for int4/uint4; the pinned TVM importer must accept the complete resulting graph and opset, not just the two custom nodes.
4. Feed that exact graph through the existing specialization and TVM build. Demonstrate output parity against the official PyTorch path at several supported lengths up to 1,024, and record the wrapper revision, export/quantizer versions and options, source hashes, graph and external-weight hashes, TVM source commit, build options, and numerical comparison results in the new artifact record.

The likely hard part is step 2: the official Python encoder constructs restarted positions and a dense 4-D block mask outside the model. The current two-input graph contract does not carry these explicitly, and no official export wrapper is available. A first prototype should resolve this before spending time on full 4-bit conversion.

That is a **compatible recipe**, not a bit-exact historical recipe: the exact official ONNX exporter invocation, ONNX Runtime quantizer version/config used to make the Hugging Face ONNX graph, and export wrapper source are not in the official Kev checkpoint. Pin the custom wrapper commit, export and quantizer versions, all quantization exclusions/axes, opset, external-data layout, and output hashes in the new artifact record. Compare outputs against `kev/evaluate.load()` on fixed multi-question examples before accepting the graph.

The [Kev code repository](https://github.com/jaredpalmer/kev/blob/37cb2f6155afec1054de2cc78dfd7c7dd24a956d/LICENSE) also has an Apache-2.0 license. For redistribution, include copies of the Kev and Qwen license texts, identify both upstream projects and pinned revisions, and state that the checkpoint was merged, exported, and quantized for TVM. The Kev model card says each training dataset has its own license; that dataset-rights scope is separate from the checkpoint's declared license and was not audited here.

## Viability and remaining unknowns

The historical ONNX recipe is not the replacement plan. The direct PyTorch wrapper and single-case TVM CPU path now execute; Q4, dynamic-shape behavior, WebGPU, package integration, numerical coverage, and rights review remain unverified. Training encoder defaults are 384/1,024, while the official serving path sets both state and branch limits to 8,192. The serving limit, rather than the training default, is the package compatibility target.

The current attention experiment compiles as a TVM WebGPU module and passes a 129-token synthetic dispatch with zero-work tails. On Chrome 157 / Intel Gen-12LP, an 8,192-token synthetic single-layer probe fails with the production 512-query setting after 6 of 16 dispatches. A diagnostic 128-query override completed 64 dispatches in 53.76 seconds, but the production graph is still configured for 512 queries and the probe used zero Q/K and constant V. Full-model maximum-length inference remains unverified; see the [chunk sweep report](../tools/kev-converter/reports/kev-attention-query-chunk-sweep-2026-11-12.json).

Still unestablished: parity across representative and maximum inputs; dynamic-shape export and compilation; WebGPU compilation and browser execution; integration into the curated package; online integrity checks and offline cache reuse for the exact artifact; and the rights/notice review for the model and its training data.

**Confidence:** high for pinned source files, hashes, checkpoint flags, official model assembly, and one-case direct Q4 CPU execution; unverified for dynamic/full-range Q4 WebGPU delivery and release readiness.
